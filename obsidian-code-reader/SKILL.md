# Code Reader

代码仓库深度解读技能，系统性地分析 Git 仓库并将解读成果写入 Obsidian 知识库。

核心思路：像一位资深架构师 review 项目一样，从全局到细节、从架构到实现，逐层解剖代码仓库，产出结构化的知识笔记。每个仓库在 vault 中独立成目录，笔记之间通过 Wikilink 形成知识网络。

## Command 总览

| Command | 作用 | 触发场景 |
|---------|------|---------|
| `仓库解读` | 深度解读代码仓库，生成结构化知识笔记 | "解读这个仓库"、"分析一下这个项目" |
| `知识检索` | 通过索引导航查找已解读的代码知识 | "之前解读过的 X 模块怎么实现的" |
| `仓库同步` | 检测仓库变更，增量更新已有解读 | "同步一下仓库变更"、"代码更新了" |
| `索引重建` | 重新扫描生成所有 `_index.md` | "重建索引" |

---

## 索引系统规范

沿用 obsidian-compendium 的渐进式索引机制。每个目录维护一份 `_index.md`，检索时逐级读取定位目标笔记。

### 索引文件格式

```markdown
---
更新时间: YYYY-MM-DD HH:mm
笔记总数: N
---

# [目录名] 索引

> 共 N 篇笔记（含子目录），最后更新: YYYY-MM-DD

## 子目录

| 子目录 | 笔记数 | 关键主题 |
|--------|--------|---------|
| <子目录A>/ | 5 | 主题1, 主题2 |

## 本目录笔记

| 笔记 | 一句话摘要 | 标签 | 创建时间 |
|------|-----------|------|---------|
| 笔记文件名 | 30字以内摘要 | 标签1, 标签2 | YYYY-MM-DD |
```

**关键规则：**
1. 子目录表和本目录笔记表按需出现
2. 一句话摘要从笔记「核心要点」首段提炼，30 字以内
3. 笔记总数递归累计，`_index.md` 本身不计入
4. 索引文件名固定为 `_index.md`

### Vault 中的仓库组织结构

所有代码仓库的解读笔记统一存放在 vault 根目录下的 `代码解读/` 目录中，每个仓库独立一个子目录：

```
<vault根>/
├── _index.md                      ← vault 顶层索引
├── 代码解读/
│   ├── _index.md                  ← 所有仓库的索引总览
│   ├── repo-name-A/
│   │   ├── _index.md              ← 该仓库的索引
│   │   ├── _repo_meta.md          ← 仓库元数据（同步追踪用）
│   │   ├── 项目概览.md
│   │   ├── 架构设计.md
│   │   ├── 模块/
│   │   │   ├── _index.md
│   │   │   ├── 模块A-核心逻辑.md
│   │   │   └── 模块B-数据处理.md
│   │   ├── 核心流程/
│   │   │   ├── _index.md
│   │   │   └── 用户认证流程.md
│   │   ├── 数据模型/
│   │   │   ├── _index.md
│   │   │   └── 数据库ER关系.md
│   │   └── API接口/

## 仓库元数据：`_repo_meta.md`

每个仓库目录下维护一份 `_repo_meta.md`，记录仓库信息和同步状态，是 `仓库同步` 功能的核心依赖。

```markdown
---
仓库名称: repo-name
仓库路径: /absolute/path/to/repo
远程地址: git@github.com:user/repo.git
默认分支: main
上次解读commit: abc1234def5678
上次解读时间: YYYY-MM-DD HH:mm
解读分支: main
---

**映射规则：**
- 一个笔记可能对应多个源文件（如「认证模块」笔记覆盖整个 `src/auth/` 目录）

- `解读范围` 标注这条映射是文件级还是目录级，帮助 sync 时判断影响范围

## Command 1: 仓库解读

### 步骤 1: 检查 Vault 配置

Vault 配置保存在用户级公共路径 `~/.agents/config/obsidian_vault.txt`，所有 Obsidian 相关 skill 共享此配置。

**配置查找优先级**：
1. `~/.agents/config/obsidian_vault.txt` ← 公共配置（推荐）
2. 如果不存在 → 询问用户 vault 名称，用 `find ~ -maxdepth 3 -name "<vault名称>" -type d` 定位后保存到 `~/.agents/config/obsidian_vault.txt`

格式：
```
<vault名称>
<vault绝对路径>
```

### 步骤 2: 确认目标仓库

确定要解读的 Git 仓库：

1. 如果用户指定了仓库路径 → 直接使用
2. 如果用户没指定 → 检查当前工作目录是否是 git 仓库（`git rev-parse --is-inside-work-tree`）
3. 都不是 → 询问用户

确认后收集仓库基本信息：
```bash
# 仓库名称（从目录名或 remote 提取）
basename $(git rev-parse --show-toplevel)
# 远程地址
git remote get-url origin
# 当前分支
git branch --show-current
# 最新 commit
git rev-parse HEAD
# 项目语言（通过文件后缀统计）
find . -type f -name "*.py" -o -name "*.js" -o -name "*.ts" -o -name "*.java" -o -name "*.go" -o -name "*.rs" | head -50
```

### 步骤 3: 检查是否已有解读

检查 `<vault>/代码解读/<仓库名>/` 目录是否已存在：
- **已存在** → 读取 `_repo_meta.md`，提示用户："该仓库已有解读记录（上次解读: YYYY-MM-DD，commit: abc1234）。要增量更新请用「仓库同步」，要全量重新解读请确认。"
- **不存在** → 继续全量解读

### 步骤 4: 全局扫描

先建立对仓库的全局认知，这一步决定后续解读的组织结构。

**4.1 目录结构分析**
```bash
# 获取项目树状结构（限制深度 4 层，排除常见非源码目录）
find . -maxdepth 4 -type f \
  ! -path './.git/*' \
  ! -path './node_modules/*' \
  ! -path './.venv/*' \
  ! -path './vendor/*' \
  ! -path './target/*' \
  ! -path './build/*' \
  ! -path './dist/*' \
  ! -path './__pycache__/*' \
  ! -path './*.pyc' \
  | head -200
```

**大仓库降级**：如果文件数超过 500，只分析核心目录（src/, lib/, app/），跳过 test/、docs/ 等辅助目录；超过 2000 则询问用户关注哪些模块，做局部解读。

**4.2 入口文件识别**

按优先级读取以下文件，快速建立项目认知：
1. `README.md` / `README.rst` — 项目说明
2. `package.json` / `pyproject.toml` / `pom.xml` / `go.mod` / `Cargo.toml` — 依赖和项目配置
3. `docker-compose.yml` / `Dockerfile` — 部署架构
4. `.env.example` / `config/` — 配置体系
5. 入口文件（`main.py`, `app.py`, `index.ts`, `Application.java` 等）

**4.3 确定解读维度和组织结构**

根据扫描结果，制定解读计划。读取 `references/analysis-dimensions.md` 获取各维度的详细分析方法。

基本维度（必选）：
- **项目概览** — 项目定位、技术栈、目录结构
- **架构设计** — 整体架构、分层设计、核心设计决策

按需维度（根据项目特点选择）：
- **模块解读** — 按模块逐个深入分析
- **核心流程** — 关键业务流程的调用链
- **数据模型** — 数据库设计、实体关系
- **API 接口** — 对外接口定义
- **配置体系** — 配置管理方式
- **依赖关系** — 内部模块依赖、外部依赖

向用户展示解读计划并确认：
```
仓库: repo-name
语言: Python (Flask)
计划生成笔记:
  1. 项目概览
  2. 架构设计
  3. 模块/ (预计 5 篇)
     - 认证模块-JWT鉴权
     - 用户管理-CRUD
     - ...
  4. 核心流程/ (预计 2 篇)
  5. 数据模型/ (预计 1 篇)
  6. API接口/ (预计 1 篇)

预计总笔记数: ~11 篇
确认开始？
```

### 步骤 5: 逐维度深度解读

确认后开始逐维度解读。每个维度的具体分析方法参见 `references/analysis-dimensions.md`。

**解读原则：**

1. **代码片段为王** — 每篇笔记必须包含实际代码片段。不是大段粘贴，而是精选关键实现，用代码说话。例如解读认证模块时，贴出 JWT 验证的核心函数，而不是空泛地说"使用 JWT 进行认证"。

2. **从调用者视角出发** — 解读一个模块时，先说明它被谁调用、在整体架构中的位置，再深入内部实现。读者需要先理解"为什么需要这个模块"，才能理解"它怎么实现的"。

3. **关键函数必须解读** — 对于核心/复杂函数，给出：函数签名、职责说明、关键实现逻辑、入参出参、调用的下游依赖。简单的 getter/setter/工具函数一笔带过。

4. **设计决策要解释** — 遇到非平凡的设计选择（为什么用这个库、为什么这样分层、为什么这里用了缓存），要分析原因。这是最有价值的知识。

5. **保持源码路径引用** — 每个代码片段标注来源文件路径和行号区间，方便溯源。

### 步骤 6: 生成笔记

**笔记模板：**

```markdown
---
创建时间: YYYY-MM-DD HH:mm
更新时间: YYYY-MM-DD HH:mm
标签: [仓库名, 技术栈, 模块名]
来源仓库: repo-name
源码路径: src/auth/
---

> 一句话说明这个模块/流程/模型在项目中的角色。

在 [[架构设计]] 中，该模块位于 XXX 层，负责 YYY。

## 核心实现

说明文字...

### 子主题 B

...

## 关键设计决策

- **为什么用 XXX 而不用 YYY**: 原因...
- **这个抽象层的意义**: ...

## 依赖关系

```

**文件名规则（同 obsidian-compendium）：**
1. 禁止使用 `.`，用 `-` 代替
2. 反映核心内容，2-4 个关键词用 `-` 连接
3. 示例：`认证模块-JWT鉴权`、`用户认证流程`、`数据库ER关系`

**写入方式：使用 Write 工具直接写文件到 vault 目录**，不要用 shell heredoc。

### 步骤 7: 建立笔记间的 Wikilink 网络

代码仓库的笔记天然有丰富的关联关系。在生成笔记时应充分利用 Wikilink：

**必须建立的链接：**
- **架构 → 模块**：架构设计中提到某模块时，链接到模块解读笔记
- **模块 → 模块**：模块之间有调用关系时，互相链接
- **流程 → 模块**：流程中涉及的模块都要链接
- **数据模型 → 模块**：使用该模型的模块要链接

**Wikilink 使用方式：**
- 集中引用：在 `## 相关笔记` 或 `## 依赖关系` 章节列出
- 行内引用：正文提到相关概念时自然使用 `[[笔记名]]` 或 `[[笔记名|显示文本]]`
- 跨仓库引用：如果 vault 中有其他仓库的笔记也相关，使用 `[[代码解读/其他仓库/笔记名]]`

**反向补链：** 生成新笔记后，检查已写入的相关笔记，在其 `## 依赖关系` 或 `## 相关笔记` 中追加反向链接。

### 步骤 8: 生成 `_repo_meta.md`

解读完成后，生成仓库元数据文件。遍历所有生成的笔记，构建完整的文件-笔记映射表。

### 步骤 9: 维护索引

从仓库目录开始，向上更新所有层级的 `_index.md`，直到 vault 根目录。

逻辑同 obsidian-compendium：
1. 笔记所在目录 → 追加笔记条目
2. 上级目录 → 更新子目录的笔记数和关键主题
3. 一直到 vault 根目录

增量更新，不全量重建。

### 步骤 10: Git 自动同步

读取 `references/git-sync.md` 执行 vault 的 Git 同步流程。

## Command 2: 知识检索

### 步骤 1: 检查 Vault 配置

同「仓库解读」步骤 1。

### 步骤 2: 理解检索意图

分析用户的问题：
- 在找哪个仓库的什么内容？
- 需要什么深度？（概览 / 某个模块的实现细节 / 某个函数的具体逻辑）

### 步骤 3: 渐进式索引导航

```
1. 读取 <vault>/代码解读/_index.md
   → 了解已解读的所有仓库

2. 读取目标仓库的 _index.md
   → 看到该仓库的解读维度和笔记列表

3. 根据问题缩小范围，进入子目录的 _index.md
   → 定位到具体笔记

```

**多仓库探索**：如果问题涉及多个仓库（如"A 仓库和 B 仓库的认证方式有什么不同"），同时探索多个仓库分支。

### 步骤 4: 兜底搜索

索引导航无法定位时，使用 Grep 工具在 `<vault>/代码解读/` 目录下搜索关键词：

```
Grep pattern="<关键词>" path="<vault>/代码解读/"
```

### 步骤 5: 整理回答

**有相关笔记：**
```
在 [仓库名] 的解读中找到：

[笔记名]
路径: 代码解读/repo-name/模块/认证模块-JWT鉴权

```

**无相关笔记：**
```

- 该部分代码未被覆盖 → 可以补充解读
- 换个关键词试试
```

## 笔记中的代码片段规范

代码片段是本 skill 与 obsidian-compendium 最大的区别。以下是代码片段的书写规范：

### 格式要求

每个代码片段必须包含：
1. **源文件路径和行号**（作为注释放在代码块第一行）
2. **语言标记**（用于语法高亮）
3. **精选的代码**（不是全文粘贴，而是关键片段）

```markdown
` ``python
# src/auth/jwt.py:15-32
def verify_token(token: str) -> dict:
    """验证 JWT token"""
    payload = jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
    return payload
`` `
```

### 什么时候贴代码

| 场景 | 是否贴代码 | 说明 |
|------|-----------|------|
| 核心业务逻辑 | 是 | 精选关键函数 |
| 设计模式的实现 | 是 | 展示模式的具体应用 |
| 复杂算法 | 是 | 配上注释解释 |
| 配置文件的关键部分 | 是 | 如数据库连接、中间件注册 |
| 简单 CRUD | 否 | 文字描述即可 |
| getter/setter | 否 | 不值得占篇幅 |
| 第三方库的标准用法 | 视情况 | 有定制化才贴 |

### 代码片段长度控制

- 单个片段不超过 30 行
- 超过的用 `# ... (省略 N 行)` 标记
- 重点标注关键行，用注释说明
