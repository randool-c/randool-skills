# Obsidian Compendium

个人知识库管理技能，通过**渐进式索引**完成**沉淀 → 检索**的闭环。

核心思路：每个目录维护一份 `_index.md` 摘要，检索时逐级读取索引定位目标笔记，而非盲搜全库。类似技能系统的渐进式披露——先看概览，再深入细节。

## Command 总览

| Command | 作用 | 触发场景 |
|---------|------|---------|
| `知识沉淀` | 把学到的东西存到 Obsidian + 自动维护索引 | "记一下这个"、"保存到 Obsidian" |
| `知识检索` | 通过索引导航找到笔记并整理回答 | "找找我记过的 X"、"我之前关于 Y 记过什么" |
| `索引重建` | 扫描 vault 重新生成所有 _index.md | "重建索引"、"刷新知识库索引" |

---

## 索引系统规范

索引是整个 skill 的核心机制，沉淀和检索都依赖它。先理解索引规范，再看具体 Command。

### 索引文件：`_index.md`

每个包含笔记或子目录的目录下都有一份 `_index.md`，作为该目录的「目录页」。

**格式规范：**

```markdown
---
更新时间: YYYY-MM-DD HH:mm
笔记总数: N
---

# [目录名] 索引

> 共 N 篇笔记（含子目录），最后更新: YYYY-MM-DD

## 子目录

| 子目录 | 笔记数 | 关键主题 |
|--------|--------|---------|
| <子目录A>/ | 5 | 主题1, 主题2 |
| <子目录B>/ | 3 | 主题3, 主题4 |

## 本目录笔记

| 笔记 | 一句话摘要 | 标签 | 创建时间 |
|------|-----------|------|---------|
| 笔记文件名(不含.md) | 30字以内的核心内容摘要 | 标签1, 标签2 | YYYY-MM-DD |
```

**关键规则：**

1. **子目录表**和**本目录笔记表**按需出现——没有子目录就不写子目录表，没有直属笔记就不写笔记表
2. **一句话摘要**从笔记的「核心要点」首段提炼，控制在 30 字以内
3. **笔记总数**包含所有子目录中的笔记（递归累计）
4. `_index.md` 本身不计入笔记总数
5. 索引文件名固定为 `_index.md`，Obsidian 中可通过设置排除在图谱外

### 索引层级示例

以下展示索引如何从 vault 根目录逐层覆盖：

```
<vault根>/
├── _index.md              ← 顶层：列出所有一级分类 + 笔记数 + 关键主题
├── 学习/
│   ├── _index.md          ← 二级：列出子目录或直属笔记
│   ├── 技术/
│   │   ├── _index.md
│   │   ├── 后端/
│   │   │   ├── _index.md  ← 叶子：列出具体笔记标题 + 一句话摘要
│   │   │   └── 某篇笔记.md
│   │   └── 前端/
│   │       ├── _index.md
│   │       └── 另一篇笔记.md
│   └── 方法论/
│       ├── _index.md
│       └── 又一篇笔记.md
├── 生活/
│   ├── _index.md
│   └── 某篇生活笔记.md
└── 工作/
    ├── _index.md
    └── 某篇工作笔记.md
```

每个 `_index.md` 只描述**当前目录的直接子目录和直属笔记**，不跨级。检索时从顶层逐级读取，像翻书的目录一样逐步深入。

### 跨领域引用

一篇笔记只存放在**一个**物理位置，但可以被多个索引引用。

当笔记涉及多个领域时（如"Docker 部署 PostgreSQL"），在主分类之外的相关 `_index.md` 中增加引用条目：

```markdown
## 跨领域引用

| 笔记 | 实际路径 | 一句话摘要 |
|------|---------|-----------|
| Docker-部署-PostgreSQL | ../DevOps/Docker/Docker-部署-PostgreSQL | 用 Docker Compose 部署 PostgreSQL 并配置持久化 |
```

跨领域引用是可选的，仅在笔记明确涉及当前目录领域时才添加。

## Command 1: 知识沉淀

### 步骤 1: 检查 Vault 配置

Vault 配置保存在用户级公共路径 `~/.agents/config/obsidian_vault.txt`，所有 Obsidian 相关 skill 共享此配置。

**配置已存在**：
直接读取获取 vault 名称和绝对路径，继续步骤 2。

**配置不存在（首次使用）**：
1. 提醒用户：**建议使用一个专门的新 vault 来存放笔记**。本 skill 会在 vault 中创建 `_index.md` 索引文件、管理 `.gitignore`、执行 git 操作等，如果使用已有的个人 vault，可能与现有内容冲突或产生意外覆盖。
2. 询问用户：你的 Obsidian vault 名称是什么？
3. 用 `find ~ -maxdepth 3 -name "<vault名称>" -type d` 定位 vault 的绝对路径
4. 将 vault 名称和绝对路径保存到 `~/.agents/config/obsidian_vault.txt`，格式如下：
   ```
   <vault名称>
   <vault绝对路径>
   ```
5. 继续步骤 2

### 步骤 2: 分析内容

分析要记录的内容，确定：
- **内容性质**：技术问题 / 技术概念 / 生活心得 / 项目经验 / 方法论
- **技术栈/领域**：前端/后端/数据库/DevOps/AI 等
- **具体技术**：React/Docker/PostgreSQL 等
- **知识点层级**：从粗到细，如 `后端/Java/Spring Boot/`

### 步骤 3: 确定分类路径

分类路径由内容分析完全决定，从 vault 根目录开始逐层组织，不受固定前缀限制。例如技术笔记可能是 `学习/技术/后端/Java/`，生活笔记可能是 `生活/`，工作笔记可能是 `工作/项目经验/`。

**路径确定时参考已有索引**：先读取 vault 根目录的 `_index.md`（如果存在），了解已有的一级分类结构，然后逐级深入目标区域的索引。尽量复用已有目录，避免创建语义重复的新目录（比如已有 `Vue/` 就不要再建 `Vue3/`）。如果是全新领域，根据内容性质自行创建合理的目录层级。

### 步骤 4: 生成文件名（重要）

**Obsidian CLI 对 `.` 敏感，会当作分隔符处理，导致文件名截断。**

命名规则：
1. **禁止使用 `.`**，用 `-` 代替
2. 文件名应反映**核心内容要点**，而非宽泛标题
3. 提炼 2-4 个关键词，用 `-` 连接

示例：
| 内容概要 | 错误 | 正确 |
|---------|------|------|
| Next.js App Router 的文件系统路由机制 | Next.js.md | Nextjs-AppRouter-文件系统路由 |
| React useEffect 的依赖陷阱 | React-Hooks.md | React-useEffect-依赖陷阱 |

### 步骤 5: 生成笔记内容

```markdown
---
创建时间: {{timestamp}}
标签: [{{tags}}]
来源: {{source}}
---

# {{title}}

## 核心要点
{{key_points}}

## 相关笔记（有关联笔记时才出现）
{{related_notes_wikilinks}}

## 补充说明（有补充内容时才出现）
{{additional_notes}}

## 来源对话（有对话摘要时才出现）
{{conversation_summary}}
```

字段说明：
- `timestamp`: `YYYY-MM-DD HH:mm`
- `tags`: `#Java #Spring #依赖注入` 格式
- `source`: `与 Claude 的对话 - YYYY-MM-DD`
- `title`: 反映内容要点的标题（不同于文件名）
- `key_points`: 提炼的核心知识点
- `related_notes_wikilinks`: 通过步骤 5.5 发现的关联笔记（见下文）
- `additional_notes`: 补充说明，无内容时省略整个章节
- `conversation_summary`: 对话摘要，无内容时省略整个章节

**条件渲染**：`## 相关笔记`、`## 补充说明`、`## 来源对话` 三个章节内容为空时直接省略，不要留空章节。只有 `## 核心要点` 是必须出现的。

### 步骤 5.5: 发现关联笔记并生成 Wikilinks

笔记内容确定后、写入文件前，利用已有索引发现关联笔记，用 Obsidian 的 `[[wikilink]]` 语法建立双向链接。

**发现流程：**

1. 读取新笔记**所在目录**及**相邻目录**的 `_index.md`，扫描同领域笔记的标题和摘要
2. 读取**上一级目录**的 `_index.md`，检查其他子领域中是否有主题交叉的笔记（通过关键主题字段判断）
3. 如果发现有关联的笔记（主题重叠、技术栈相关、概念有因果/对比关系），收集其文件名

**关联判断标准（至少满足一项）：**
- **同一技术栈**：如新笔记讲 React Hooks，已有笔记讲 React 组件生命周期
- **概念上下游**：如新笔记讲 SQL 索引优化，已有笔记讲数据库连接池
- **问题-方案对**：如新笔记记录某个报错的解决方案，已有笔记记录了同技术栈的另一个问题
- **对比关系**：如新笔记讲 Pinia，已有笔记讲 Vuex

**不要过度关联**——只链接真正有阅读价值的关联笔记。宁可少链，不要泛链。

**正文中自然使用 Wikilink**：除了 `## 相关笔记` 章节的集中引用外，在笔记正文（核心要点、补充说明等）中提到已有笔记涵盖的概念时，也应自然地使用 `[[笔记名]]` 内联引用。例如，正文中提到"连接池"时，如果知识库中已有相关笔记，可以写成 `[[连接池相关笔记名|连接池]]`（使用 Obsidian 的别名语法保持行文自然）。

**生成 `## 相关笔记` 内容：**

```markdown
## 相关笔记

- [[笔记A的文件名（不含.md）]]：一句话说明关联原因
- [[笔记B的文件名（不含.md）]]：一句话说明关联原因
```

如果没有发现关联笔记，省略整个 `## 相关笔记` 章节。

**反向补链（重要）：**

发现关联后，不仅在新笔记中添加 `[[旧笔记]]` 链接，还要**在旧笔记中追加对新笔记的反向链接**。

操作方式：读取旧笔记 → 在其 `## 相关笔记` 章节追加一行 `[[新笔记文件名]]`。如果旧笔记没有 `## 相关笔记` 章节，在 `## 补充说明` 之前插入。

这样两篇笔记之间形成真正的**双向链接**，在 Obsidian 的图谱视图中可以直观看到知识网络。

### 步骤 6: 执行创建

**使用 Write 工具直接写文件到 vault 目录**，不要用 `obsidian create` 的 `content=` 参数。

原因：`obsidian create content=...` 通过 shell heredoc 传递内容时，markdown 中的反引号会被 shell 转义为 `\``，导致代码块在 Obsidian 中不可读。Write 工具直接写入文件系统，没有 shell 转义问题。

```
写入路径：<vault绝对路径>/<分类路径>/<文件名>.md
```

vault 绝对路径直接从 `vault_path.txt` 第二行读取，无需每次 find。

### 步骤 7: 维护索引（关键步骤）

笔记写入后，**必须更新沿途所有层级的 `_index.md`**。这是索引系统的核心——沉淀时维护，检索时受益。

**执行逻辑：**

1. 从笔记所在目录开始，向上遍历到 vault 根目录
2. 对每一级目录：
   - 如果 `_index.md` 不存在 → 创建新索引，扫描该目录下的子目录和 `.md` 文件生成完整索引
   - 如果 `_index.md` 已存在 → 读取后增量更新：
     - **笔记所在目录**：在「本目录笔记」表中追加新条目
     - **上级目录**：更新「子目录」表中对应子目录的笔记数和关键主题
3. 更新 frontmatter 中的 `更新时间` 和 `笔记总数`

**示例：** 假设写入 `学习/技术/后端/Java/Spring-DI.md` 后：

```
需要更新的索引（从下往上）：
1. 学习/技术/后端/Java/_index.md     ← 追加笔记条目
2. 学习/技术/后端/_index.md          ← 更新 Java/ 的笔记数
3. 学习/技术/_index.md               ← 更新 后端/ 的笔记数
4. 学习/_index.md                    ← 更新 技术/ 的笔记数
5. _index.md                         ← 更新 学习/ 的笔记数（vault 根索引）
```

**增量更新而非全量重建**：只修改变化的部分，对于已有的其他条目保持不动。这样即使 vault 很大，每次沉淀的索引维护开销也很小。

### 步骤 8: Git 自动同步

执行「Git 自动同步」流程（见下文独立章节）。

### 主动触发逻辑

在以下情况主动询问是否记录：
- 讨论了新的技术概念、框架、工具
- 解决了重要的技术问题
- 用户表达了重要的决策或结论
- 发现了值得记录的方法论或最佳实践

询问方式：
```
"要把这个 [知识点/问题/概念] 记到 Obsidian 吗？
建议存到：[路径]
标签：[标签]
文件名：[文件名]
直接说'记'我就执行。"
```

### 交互约定

- **直接要求记录** → 立即执行（包括步骤 7 索引维护）
- **询问确认** → 用户说"记"/"好" → 执行；说"不用"/"算了" → 跳过
- **用户指定路径** → 按用户意图执行

## Command 2: 知识检索

### 步骤 1: 检查 Vault 配置

同「知识沉淀」的步骤 1。

### 步骤 2: 理解检索意图

分析用户的问题：
- 用户在找什么？（主题/技术/概念）
- 需要什么深度的信息？（概要/详细/具体操作）
- 有没有限定范围？（某个技术栈/某个时间/某个目录）

### 步骤 3: 渐进式索引导航（核心）

这是与旧版最大的不同。不再直接 `obsidian search`，而是**逐级读取 `_index.md` 定位目标**。

**导航流程：**

```
1. 读取顶层 _index.md
   → 了解所有子领域及其笔记数和关键主题
   → 判断用户问题可能涉及哪个/哪几个子领域

2. 读取选中子领域的 _index.md
   → 看到更细分的目录或具体笔记列表
   → 继续缩小范围

3. 到达叶子目录（包含具体笔记的 _index.md）
   → 阅读笔记摘要，选出与问题最相关的笔记

4. 读取目标笔记的完整内容
```

**多分支探索**：如果用户的问题涉及多个领域，可以同时探索多个分支，读取多个 `_index.md`。

**跨领域引用**：如果 `_index.md` 中有「跨领域引用」部分，也要检查其中是否有相关笔记。

**示例：** 用户问"我之前记过 XXX 相关的东西吗？"

```
读 <vault根>/_index.md
  → 从关键主题中判断 XXX 属于哪个一级分类（学习/生活/工作...）
  → 进入对应子目录

读 <一级分类>/_index.md
  → 看到更细的分类或具体笔记
  → 继续深入

读 <叶子目录>/_index.md
  → 从笔记摘要中确认哪篇相关
  → 读取目标笔记全文
```

整个过程通常只需读 2-4 个索引 + 1-2 篇笔记，无论 vault 中有多少篇笔记。

### 步骤 4: 兜底搜索

如果索引导航无法定位（比如索引不存在、索引中没有匹配的条目、或用户的关键词太模糊），回退到关键词搜索：

```bash
obsidian search vault=<vault名称> query=<关键词> limit=10
```

兜底搜索的结果同样逐个读取后分析关联度。

**什么时候触发兜底：**
- 顶层 `_index.md` 不存在（vault 未建立索引）
- 索引导航走完所有分支都没找到相关笔记
- 用户的问题太泛，无法从索引中判断方向

### 步骤 5: 整理并回答

根据分析结果，给用户整理回答：

**如果有相关笔记**：
```
我在你的知识库里找到了相关内容：

[文件名]
路径：xxx
核心要点：...

[文件名2]
...

---
综合回答你的问题：[基于笔记内容的整理回答]
```

**如果没有相关笔记**（索引导航 + 兜底搜索均无果）：
```
我在你的知识库里没有找到直接相关的内容。
可能的方向：
- 可以换个关键词试试
- 如果是新话题，要不要记一下？
```

### 主动触发逻辑

在以下情况主动建议检索：
- 用户问了一个技术问题，你感觉他可能之前记过
- 用户提到"我之前好像记过..."
- 用户说"找找我记的..."

### 交互约定

- **明确检索需求** → 直接执行索引导航
- **不确定表述**（"好像记过"）→ 确认后再搜
- **找不到** → 提供替代建议，可以建议记录

## Command 3: 索引重建

当 vault 中已有大量笔记但没有索引时（比如首次启用渐进式索引），或索引与实际笔记不同步时，执行全量重建。

### 执行逻辑

1. 从 vault 根目录开始，递归扫描所有子目录
2. 对每个包含 `.md` 文件或子目录的目录，生成 `_index.md`：
   - 扫描子目录，统计各自的笔记数（递归）
   - 扫描本目录的 `.md` 文件（排除 `_index.md`），读取 frontmatter 提取标签和创建时间
   - 读取笔记「核心要点」首段，提炼一句话摘要
3. 自底向上生成，确保子目录的笔记数统计准确
4. **输出进度**：每处理完一个目录，输出一行进度（如 `✓ 领域A/子领域A1/ — 3 篇笔记`），让用户感知重建进度

### 索引重建后同步

重建完成后，执行「Git 自动同步」流程（见下文独立章节）。

### 触发方式

- 用户说"重建索引"/"刷新索引"
- 检索时发现大量目录缺少 `_index.md`，主动建议重建
